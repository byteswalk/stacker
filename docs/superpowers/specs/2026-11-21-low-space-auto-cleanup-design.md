# 空间不足自动清理

日期：2026-11-21　状态：已实现，待用户验收

## 需求（用户原话）

默认开启、可以关闭；无论哪个盘，剩余空间小于等于 5%（可调）时自动清理：先清开发产物，再不行清缓存与下载；C 盘还额外清用户和系统的临时缓存，以及可安全清理的各类东西。

## 做法

后台每 5 分钟看一次本机固定磁盘（启动后 90 秒第一次看）。某块盘剩余 ≤ 设定比例时，按步骤清理：

| 步骤 | 内容 | 何时停 |
|---|---|---|
| 闲置项目的开发产物 | 项目或这个构建目录 N 天（沿用「会话数据 · 残留」的项目闲置天数，默认 7）没写入的 `target`、`dist`、`build`、`.next`、`bin/obj`、Python 与工具缓存 | 整步清完（闲置产物没有价值） |
| 在用项目的开发产物 | 其余构建产物，最久没构建的先清 | 剩余达到设定值两倍即停 |
| 缓存与下载 | 闲置天数内没写入过、读它的工具也没在运行的包管理器下载缓存（已知规则里标为安全的），再到闲置项目的 `node_modules`、`.gradle` | 同上 |
| 临时文件与系统缓存 | 7 天没写入的临时目录条目（以管理员身份运行时含 `C:\Windows\Temp`）、浏览器缓存、崩溃转储、网页组件缓存、显卡着色器缓存、Windows 错误报告、编辑器缓存（VS Code 系） | 同上 |

下一步只在磁盘仍 ≤ 设定比例时才开始。临时文件和这些缓存都在系统盘，所以「C 盘额外清理」自然只发生在 C 盘。

同一块盘清过一次后：1 小时内不再清；之后要等又用掉 1 GB 以上，或过了一天。页面上的「立即检查」不受这个限制，也不受开关限制。

## 安全边界

- 项目来源：智能体会话的工作目录，加上磁盘遍历找到的、在 Git 管理下的项目（遍历不进隐藏目录、系统与程序目录、AppData、`node_modules`）。
- 一律不动：安装在 Program Files 之外的程序（`resources\app`、`.asar.unpacked`）、`site-packages`、`node_modules` 里的包；`out` 目录（常是渲染出的视频或导出的应用）；虚拟环境、发布包、日志；30 分钟内写过的目录；正在运行的程序所在目录；`%TEMP%\claude`（会话残留按会话活动清）；回收站、源码、文档、模型。
- 删除尽量多删，遇到被占用的文件跳过继续；链接和联接只删链接本身，路径须解析在被清理的目录内。
- 每次运行写入设置文件（最近 20 次）和「清理记录」，窗口里给出通知；窗口隐藏时，下次显示再告知。

## 真机运行后的修正（2026-11-21）

用户打开开关后，D 盘的 cargo 源码与下载缓存一天里被删了三次：每次构建重新下载约 1.3 GB，下一次清理又删掉，最后一次删在一次正在进行的构建中间，导致链接失败（`windows.0.53.0.lib` 找不到）。现在包管理器缓存只在闲置天数内没写入、且 cargo/rustc、go、pip、uv 等读它的工具没在运行时才清。

## 实测（只读预演，2026-11-21）

首次预演发现磁盘遍历会把安装在 D 盘的 VS Code、WorkBuddy 自带的 CLI、conda 环境里的 Python 包当成项目，还会把 Remotion 渲染的 `out` 视频列进去；据此加了 Git 要求、安装位置排除和 `out` 排除。修正后各盘预演：C 盘 3.9 GB（临时文件 2.9 GB 与各类缓存），D 盘 1.2 GB（cargo 与 npm 缓存、`dist`），E/F 盘未低于阈值不会动。
